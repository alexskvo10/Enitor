# Свой сервер Enitor

Сервера Enitor у нас нет, и эта страница не про него. Она про сервер, который
запускаешь **ты**: `enitor-server` — небольшая программа, которая идёт вместе с
Enitor. Он делает две вещи:

- **Синхронизация.** Телефон и компьютер хранят полную копию твоих данных и
  обмениваются изменениями через твой сервер, поэтому у обоих в итоге одни и те
  же задачи, цели и расписание.
- **REST.** Скрипты и автоматизации (Home Assistant, n8n, командный файл)
  читают и меняют твои данные по обычному HTTP, с токеном.

Сервер стоит посередине:

```
телефон ──┐
          ├── enitor-server (твой компьютер, NAS или домашний сервер) ── REST для автоматики
компьютер ┘
```

Данные уходят только на адрес, который ты введёшь в Enitor. Ничего не уходит нам.

Точные форматы записей — в [formats.ru.md](formats.ru.md). Пошаговые рецепты
для других инструментов — в [recipes.ru.md](recipes.ru.md).

## Быстрый старт

### 1. Получи сервер

На Windows он идёт вместе с Enitor: `enitor-server.exe` лежит рядом с
`enitor.exe` в архиве релиза. В остальных случаях собери его из исходников,
через Flutter SDK:

```
dart build cli -t bin/enitor_server.dart -o build/server
```

На Windows программа лежит в `build/server/bundle/bin/enitor_server.exe`. На
Linux — по тому же пути без `.exe`. Чтобы попробовать без сборки, запусти
`dart run bin/enitor_server.dart` из папки проекта.

### 2. Запусти

```
enitor_server.exe --data C:\enitor-data
```

По умолчанию сервер слушает порт 8787 и только этот компьютер (`127.0.0.1`), а
данные хранит в папке `enitor-data`. Лучше дать абсолютный путь, чтобы данные не
зависели от того, откуда ты запустил программу.

| Опция | По умолчанию | Что значит |
|---|---|---|
| `--port <n>` | 8787 | порт |
| `--host <адрес>` | 127.0.0.1 | адрес, на котором слушать; `0.0.0.0` принимает подключения из домашней сети |
| `--data <папка>` | enitor-data | папка для данных и токена |
| `--token <t>` | — | свой токен вместо созданного; он запишется в файл токена |
| `--show-token` | — | напечатать токен и выйти |
| `-h`, `--help` | — | справка |

При первом запуске сервер создаёт токен и печатает его один раз. Токен также
лежит в файле `token` в папке данных. Посмотреть его снова:

```
enitor_server.exe --data C:\enitor-data --show-token
```

В папке данных два файла: `enitor-data.json` (все данные, обычный JSON) и
`token`. Папку стоит копировать в бэкап регулярно.

### 3. Подключи Enitor

На каждом устройстве открой **Настройки → Синхронизация → Свой сервер**, нажми
**Подключить сервер** и введи:

- **адрес**: `http://192.168.1.10:8787` дома или `https://enitor.example.com`
  снаружи (см. ниже);
- **токен**.

Затем выбери режим:

- **Объединить с данными на сервере** (по умолчанию). Твои записи уходят на
  сервер. Где запись уже есть на сервере, остаётся серверная.
- **Заменить данные этого устройства данными сервера.** Приложение сначала
  сохранит авто-бэкап, потом очистит локальные данные и загрузит данные сервера.

На экране сервера видно время последней синхронизации, кнопку **Синхронизировать
сейчас** и журнал обменов. Чтобы отключиться, нажми **Отключить**: данные
останутся на устройстве, обмен прекратится.

### 4. Дома

Запусти сервер с `--host 0.0.0.0`, разреши порт в брандмауэре, если Windows
спросит, и используй адрес компьютера в твоей сети, например
`http://192.168.1.10:8787`. Трафик идёт по обычному HTTP, поэтому любой в твоей
сети может его прочитать. Для дома это нормально. Открывать обычный HTTP в
интернет не нужно.

### 5. Снаружи дома: HTTPS

Оставь сервер на `127.0.0.1` и поставь перед ним прокси с HTTPS. Caddy получит
сертификат сам. Вот полный `Caddyfile`:

```
enitor.example.com {
	reverse_proxy 127.0.0.1:8787
}
```

Домен должен указывать на твой домашний адрес, а порты 80 и 443 должны доходить
до машины с Caddy. Потом используй в Enitor адрес `https://enitor.example.com`.
Любой другой HTTPS-прокси работает так же: ему нужно только пересылать запросы
на `127.0.0.1:8787`.

## Что синхронизируется

Синхронизируется, с именами коллекций из протокола:

- задачи, включая экземпляры повторов и отметки (`tasks`);
- цели (`goals`);
- пункты и серии расписания (`schedule`);
- правила повторов (`recurrence`);
- шаблоны дней (`templates`);
- бэклоги задач и целей (`taskBacklog`, `goalBacklog`);
- статистика дней (`dayStats`);
- оценки дней и периодов (`dayRatings`, `periodRatings`).

Не синхронизируется: профиль, настройки, достижения и всё, что хранится отдельно
на каждом устройстве: настройки синхронизации, журнал обменов, адрес для
push-сигналов и ключи интеграций. Токен хранится в защищённом хранилище каждого
устройства.

---

## Когда синхронизируется

- При запуске приложения.
- Через три секунды после твоей правки, поэтому быстрые правки уходят одним обменом.
- Когда ты возвращаешь приложение на экран.
- Пока приложение открыто, сервер сразу сообщает ему, если другое устройство
  что-то поменяло (поток событий, см. ниже). На Windows это работает и когда окно
  свёрнуто в трей.
- Раз в пять минут — запасной вариант.
- Когда ты нажимаешь **Синхронизировать сейчас**.

На Android в фоне — см. раздел [Android в фоне](#android-в-фоне).

## Конфликты

Сервер нумерует каждое изменение ревизией. Устройство присылает свои изменения
вместе с ревизией записи, которую видело последний раз (`baseRev`). Дальше
работают два правила:

- **Правка известной записи побеждает.** Если устройство правит запись, которую
  уже знало, побеждает правка, пришедшая позже: она целиком заменяет запись.
  Слияния по полям нет. Если ты поправил одну задачу на двух устройствах до
  синхронизации, сохранится правка, пришедшая позже, целиком.
- **Создание записи, которая уже есть, отвергается.** Если устройство создаёт
  запись, которая на сервере уже есть или удалена, сервер оставляет свою версию и
  возвращает её. Так два устройства, создавшие один и тот же экземпляр повтора,
  дают одну задачу, а не две.

## Удаления

Удалённая запись оставляет на сервере пометку на 90 дней, чтобы другие
устройства узнали об удалении. При запуске сервера пометки старше 90 дней
стираются. Устройство, которое молчало дольше и потом правит удалённую запись,
вернёт её. Это редкость, и ничего не теряется.

## Повторы

- Повторяющаяся задача — одно правило (`recurrence`). Каждый день, на который оно
  действует, — задача с id `r-<id правила>-<yyyymmdd>`, например
  `r-b2d4e6f8-0000-4000-8000-000000000001-20261028`. Id одинаковый на всех
  устройствах и на сервере, поэтому устройства не создают два экземпляра одного
  дня.
- Пока экземпляр никто не отметил и не поправил, он существует только как
  виртуальная строка в плане дня, с пометкой `"virtual": true`. Отметка создаёт
  настоящую запись.
- Удаление одного дня повторяющейся задачи добавляет этот день в `exceptDates`
  правила, и день не вернётся.
- Повторяющийся пункт расписания — одна запись с настройками повтора. Правка или
  удаление «только этого дня» добавляет день в `exceptDates` серии, а правка
  создаёт отдельный разовый пункт с новым id.

## Восстановление бэкапа

Восстановление бэкапа сбрасывает состояние синхронизации на устройстве: оно
отправляет записи на сервер как новые. Восстановление ничего не удаляет на
сервере. Запись, которая уже есть на сервере, остаётся серверной версией. Запись
из бэкапа, которой на сервере нет, уходит на сервер.

## Android в фоне

Android разрывает соединение, когда приложение уходит в фон, поэтому Enitor
будится одним из двух способов.

1. **UnifiedPush через ntfy (рекомендуем).** Установи **ntfy** из F-Droid или
   Google Play. Это доставщик UnifiedPush. При подключении Enitor сам
   регистрируется в нём и повторяет регистрацию при каждом запуске. Если ntfy
   поставишь позже, открой Enitor один раз. Сервер шлёт короткий сигнал через
   доставщика, когда что-то меняется. В сигнале только номер ревизии, никаких
   данных. Если доставщик работает на чужом сервере, номер проходит через него,
   и больше он ничего не узнаёт.
2. **Без ntfy.** Enitor синхронизируется в фоне примерно раз в 15 минут, когда есть
   сеть. Android может задержать это, чтобы экономить батарею.

Почему не push-сервис Google? Ему нужны сервисы Google и аккаунт. UnifiedPush
делает то же самое через доставщика, которого выбираешь ты.

## REST для автоматики

Каждый путь `/v1/` требует заголовок `Authorization: Bearer <токен>`. Ответы — в JSON:

```json
{"ok": true, "result": { ... }}
```

или, при ошибке, `{"ok": false, "error": {"code": "...", "message": "...", "field": "..."}}`.
См. [Ошибки](#ошибки).

Даты — `YYYY-MM-DD`, время — `HH:MM` (например, `09:30`). Записи используют те же
имена полей, что и экспорт. В ответах по дням даты в виде ISO, например
`2026-10-28T00:00:00.000`.

### Маршруты

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/v1/ping` | проверка сервера и токена; в `result` есть `server`, `version`, `rev` |
| GET | `/v1/days/{date}` | один день: `tasks` (с виртуальными экземплярами повторов), `schedule`, `goals` на этот день, `stats`, `rating` |
| GET | `/v1/days?from=&to=` | несколько дней, не больше 62 за запрос |
| GET | `/v1/tasks?from=&to=` | сохранённые задачи по датам; оба параметра необязательны; виртуальных экземпляров нет |
| GET | `/v1/tasks/{id}` | одна задача |
| POST | `/v1/tasks` | создать задачу |
| PATCH | `/v1/tasks/{id}` | поменять поля задачи |
| POST | `/v1/tasks/{id}/complete` | отметить задачу выполненной |
| POST | `/v1/tasks/{id}/uncomplete` | снять отметку |
| DELETE | `/v1/tasks/{id}` | удалить задачу или один день повтора |
| GET | `/v1/goals?period=&date=` | цели; оба параметра необязательны |
| GET | `/v1/goals/{id}` | одна цель |
| POST | `/v1/goals` | создать цель |
| PATCH | `/v1/goals/{id}` | поменять поля цели |
| POST | `/v1/goals/{id}/progress` | задать прогресс: `{"value": n}` |
| POST | `/v1/goals/{id}/complete` | отметить цель выполненной |
| POST | `/v1/goals/{id}/uncomplete` | снять отметку |
| DELETE | `/v1/goals/{id}` | удалить цель |
| GET | `/v1/schedule` | все пункты расписания; для одного дня используй `/v1/days/{date}` |
| GET | `/v1/schedule/{id}` | один пункт расписания |
| POST | `/v1/schedule` | создать пункт или серию |
| PATCH | `/v1/schedule/{id}` | поменять пункт; с `?scope=day&date=` — только один день серии |
| DELETE | `/v1/schedule/{id}` | удалить пункт; с `?scope=day&date=` — только один день серии |
| POST | `/v1/sync` | протокол синхронизации, см. ниже |
| PUT | `/v1/devices/{deviceId}/push` | задать или снять адрес push-сигналов устройства |
| GET | `/v1/events` | поток событий (server-sent events) |

Правила повторов через REST не создаются. Создай повтор в приложении — он
попадёт на сервер при следующей синхронизации. Или отправь запись `recurrence`
через `/v1/sync`, см. [протокол](#протокол-для-своего-сервера).

### Поля

**Задачи** (`POST` и `PATCH`):

- `title`: обязательно при `POST`. Пробелы по краям обрезаются.
- `date`: `YYYY-MM-DD`. При `POST` без него задача попадает на сегодня. «Сегодня»
  начинается в 4:00, поэтому до 4:00 это предыдущий день, как и в приложении.
- `start`, `end`: `HH:MM`.
- `priority`: `none`, `low`, `medium` или `high`.
- `done`: `true` или `false`. Ставит или снимает время выполнения.
- `progress`: целое число, для задач-счётчиков.
- Любое другое поле записывается как есть, с именами из экспорта, например
  `description`, `estimatedMinutes`, `targetCount`, `tags`, `subtasks`.

`id`, `createdAt` и `virtual` не меняются.

**Цели** (`POST` и `PATCH`):

- `title`: обязательно при `POST`.
- `period`: `week`, `month`, `season` или `year`. По умолчанию `month`.
- `date`: любой день внутри периода. По умолчанию сегодня.
- `done`: `true` или `false`.
- `progress`: общий прогресс. Сервер хранит часть, введённую вручную: общий
  прогресс минус то, что уже посчитано по связанным задачам. Если задан
  `targetCount` и он достигнут, цель выполняется.
- `targetCount` и другие поля записываются как есть.

**Пункты расписания** (`POST`, а `PATCH` — для одного дня):

- `title`: обязательно.
- `date`: `YYYY-MM-DD`, обязательно при `POST`. Для серии — первый день.
- `start`: `HH:MM`, обязательно при `POST`. `end`: `HH:MM`, необязательно.
- `repeat`: `weekly`, `monthly` или `interval`. Без него пункт разовый.
- `weekdays`: дни недели для `weekly`, от 1 (понедельник) до 7 (воскресенье).
- `weekInterval`: 1 — каждую неделю, 2 — через неделю.
- `monthDays`: числа месяца для `monthly`.
- `intervalDays`: для `interval` — каждые N дней.
- `until`: `YYYY-MM-DD`, последний день серии.
- `location`, `note`, `reminderMinutes` и другие поля записываются как есть.

`end` должен быть позже `start` (через полночь нельзя), иначе сервер ответит
`400` с `field: "end"`. Когда переносишь пункт, передавай оба.

### Частые действия

Примеры для `bash` (Git Bash, Linux, macOS). Они предполагают две переменные:

```bash
BASE=http://127.0.0.1:8787
TOKEN=вставь-сюда-свой-токен
AUTH="Authorization: Bearer $TOKEN"
```

Примеры написаны с английским текстом намеренно. Git Bash в Windows передаёт
аргументы с не-ASCII символами так, что сервер их отвергает (`Body is not UTF-8`).
Русский текст работает, если тело берётся из файла в UTF-8, например:

```bash
cat > task.json <<'EOF'
{"title":"Купить молоко","date":"2026-10-28"}
EOF
curl -s -X POST "$BASE/v1/tasks" -H "$AUTH" \
  -H "Content-Type: application/json" \
  --data-binary @task.json
```

В Windows PowerShell вызывай `curl.exe` (не `curl`: там это псевдоним) и так же
клади тело в файл.

Проверить, что сервер отвечает:

```bash
curl -s "$BASE/v1/ping" -H "$AUTH"
```

План на день:

```bash
curl -s "$BASE/v1/days/2026-10-28" -H "$AUTH"
```

Добавить задачу на день, со временем и приоритетом:

```bash
curl -s -X POST "$BASE/v1/tasks" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"title":"Buy milk","date":"2026-10-28","start":"10:30","end":"11:00","priority":"high"}'
```

Новая задача — в `result`, её id — `result.id`. Этот id подставляй в примеры
ниже вместо `TASK_ID`:

```bash
curl -s -X POST "$BASE/v1/tasks/TASK_ID/complete" -H "$AUTH"
```

Снять отметку:

```bash
curl -s -X POST "$BASE/v1/tasks/TASK_ID/uncomplete" -H "$AUTH"
```

Перенести задачу на другой день:

```bash
curl -s -X PATCH "$BASE/v1/tasks/TASK_ID" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"date":"2026-10-29"}'
```

Задать прогресс задачи-счётчика (задачи с `targetCount`):

```bash
curl -s -X PATCH "$BASE/v1/tasks/TASK_ID" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"progress":5}'
```

Удалить задачу:

```bash
curl -s -X DELETE "$BASE/v1/tasks/TASK_ID" -H "$AUTH"
```

Отметить выполненным один день повтора. Id экземпляра — `r-<id правила>-<yyyymmdd>`.
Id правила есть в поле `recurrenceRuleId` экземпляра в ответе `/v1/days`:

```bash
curl -s -X POST "$BASE/v1/tasks/r-b2d4e6f8-0000-4000-8000-000000000001-20261028/complete" -H "$AUTH"
```

Удалить один день повтора. Этот день больше не появится:

```bash
curl -s -X DELETE "$BASE/v1/tasks/r-b2d4e6f8-0000-4000-8000-000000000001-20261026" -H "$AUTH"
```

Создать цель на год, с целью 12:

```bash
curl -s -X POST "$BASE/v1/goals" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"title":"Read 12 books","period":"year","targetCount":12}'
```

Задать её прогресс: 5 из 12:

```bash
curl -s -X POST "$BASE/v1/goals/GOAL_ID/progress" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"value":5}'
```

Показать цели года, в который попадает 28 октября:

```bash
curl -s "$BASE/v1/goals?period=year&date=2026-10-28" -H "$AUTH"
```

Добавить разовый пункт расписания:

```bash
curl -s -X POST "$BASE/v1/schedule" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"title":"Physics class","date":"2026-10-28","start":"09:00","end":"10:30","location":"Room 301"}'
```

Добавить серию: пара по понедельникам, средам и пятницам до 18 декабря:

```bash
curl -s -X POST "$BASE/v1/schedule" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"title":"Physics class","date":"2026-10-26","start":"09:00","end":"10:30","repeat":"weekly","weekdays":[1,3,5],"until":"2026-12-18"}'
```

Удалить один день этой серии (например, 28 октября пару отменили):

```bash
curl -s -X DELETE "$BASE/v1/schedule/SCHEDULE_ID?scope=day&date=2026-10-28" -H "$AUTH"
```

Перенести один день серии на 11:00–12:30. Это создаёт разовый пункт на этот
день и возвращает его:

```bash
curl -s -X PATCH "$BASE/v1/schedule/SCHEDULE_ID?scope=day&date=2026-10-30" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"start":"11:00","end":"12:30"}'
```

Получить диапазон дней, например неделю:

```bash
curl -s "$BASE/v1/days?from=2026-10-26&to=2026-11-01" -H "$AUTH"
```

### Ошибки

Каждая ошибка выглядит одинаково:

```json
{"ok": false, "error": {"code": "bad_args", "message": "title is required", "field": "title"}}
```

`field` есть, когда виновато одно поле.

| HTTP-статус | `code` | Когда |
|---|---|---|
| 400 | `bad_json` | тело не JSON или не JSON-объект |
| 400 | `bad_args` | значение пропущено или в неверном виде (дата, время, приоритет, диапазон) |
| 400 | `bad_record` | запись не подходит под формат приложения |
| 400 | `bad_request` | в `/v1/sync` нет `cursor` или `changes` |
| 401 | `unauthorized` | токен не передан или неверный |
| 404 | `not_found` | нет такой записи или пути |
| 500 | `internal` | что-то пошло не так на сервере; в `message` написано что |

Неизвестный путь под `/v1/` даёт 404. Запрос `OPTIONS` даёт 204 с заголовками CORS.

## Протокол для своего сервера

Этот раздел нужен, если ты пишешь свой сервер на любом языке вместо
`enitor-server`. Эталонный сервер — лучший пример каждого правила. Его код лежит в
`lib/server/` проекта Enitor.

### Ping

`GET /v1/ping` возвращает `server`, `version` (сейчас 1) и текущий `rev`.

### Синхронизация: `POST /v1/sync`

Устройство присылает свои изменения и просит чужие:

```json
{
  "v": 1,
  "deviceId": "3f0c9a2e-7d41-4b8e-9a0c-6e5f1d2c3b4a",
  "cursor": 120,
  "changes": [
    {"coll": "tasks", "id": "c447f9d3-7a73-4e3f-83ab-f25134231936", "baseRev": 118,
     "data": {"id": "c447f9d3-7a73-4e3f-83ab-f25134231936", "title": "Buy milk",
              "date": "2026-10-28T00:00:00.000", "createdAt": "2026-10-28T09:00:00.000",
              "updatedAt": "2026-10-28T10:00:00.000"}},
    {"coll": "tasks", "id": "04667cc0-37f0-421f-ae41-62f5410bf955", "baseRev": 97, "deleted": true}
  ]
}
```

- `cursor`: последняя ревизия, которую видело устройство. В первый раз — `0`.
- `changes[].coll`: одна из коллекций `tasks`, `goals`, `schedule`, `recurrence`,
  `templates`, `taskBacklog`, `goalBacklog`, `dayStats`, `dayRatings`,
  `periodRatings`.
- `changes[].id`: id записи. Для `dayStats`, `dayRatings` и `periodRatings` это
  ключ дня или периода, например `2026-10-28T00:00:00.000`.
- `changes[].baseRev`: ревизия записи, которую устройство видело последний раз,
  или `0` для новой записи.
- `changes[].data`: вся запись в формате приложения. Оценка — это
  `{"value": n}`, где `n` от 1 до 10.
- `changes[].deleted`: `true` для удаления; тогда `data` нет.

Ответ:

```json
{
  "ok": true,
  "result": {
    "cursor": 124,
    "applied": [
      {"coll": "tasks", "id": "sync-task-1", "rev": 121}
    ],
    "changes": [
      {"coll": "tasks", "id": "04667cc0-37f0-421f-ae41-62f5410bf955", "rev": 122, "data": { ...вся запись... }},
      {"coll": "tasks", "id": "c447f9d3-7a73-4e3f-83ab-f25134231936", "rev": 123, "deleted": true}
    ],
    "errors": [
      {"coll": "nope", "id": "x", "message": "unknown record"}
    ]
  }
}
```

- `cursor`: текущая ревизия сервера. Сохрани её для следующего запроса.
- `applied`: изменения, которые сервер принял, с их новыми ревизиями.
- `changes`: все записи, которые изменились после твоего `cursor`, кроме только
  что принятых тобой. Отвергнутая запись возвращается сюда в виде версии сервера.
- `errors`: изменения, которые не применены совсем, с причиной. Неизвестная
  коллекция или запись, не подходящая под формат приложения, — это ошибка.

Правила те же, что в разделе [Конфликты](#конфликты): правка известной записи
побеждает, создание поверх существующей или удалённой записи отвергается.
Удаление требует ревизию, которую устройство знает (`baseRev` больше 0). Эталонный
сервер каждый раз пишет запись целиком и не сливает поля.

Правило повтора отправляется так же, в коллекции `recurrence`. Вот правило
«по понедельникам, средам и пятницам» с 20 октября. Экземпляры этого правила
получают id `r-<id правила>-<yyyymmdd>`, см. [Повторы](#повторы):

```json
{"v": 1, "deviceId": "3f0c9a2e-7d41-4b8e-9a0c-6e5f1d2c3b4a", "cursor": 0, "changes": [
  {"coll": "recurrence", "id": "b2d4e6f8-0000-4000-8000-000000000001", "baseRev": 0,
   "data": {"id": "b2d4e6f8-0000-4000-8000-000000000001", "taskTitle": "Drink water",
            "kind": "weekly", "weekdays": [1, 3, 5], "startDate": "2026-10-20T00:00:00.000",
            "createdAt": "2026-10-20T08:00:00.000", "updatedAt": "2026-10-20T08:00:00.000"}}
]}
```

Устройство хранит для каждой записи хэш и ревизию с прошлого обмена. Так оно
находит свои изменения без всяких пометок на записях. Устройство без такой
базы отправляет всё как новое.

### Поток событий: `GET /v1/events`

Долгий ответ с `Content-Type: text/event-stream`. Первое событие приходит сразу
с текущей ревизией. Потом — по одному событию на каждое сохранённое изменение:

```
event: changed
data: {"rev":124}
```

Строка-комментарий `: ping` приходит каждые 25 секунд, чтобы прокси не закрывали
соединение. Устройство, которое видит ревизию больше своего `cursor`, вызывает
`/v1/sync`. Поток — только подсказка: устройство, которое его пропустило,
всё равно синхронизируется раз в пять минут.

### Push: `PUT /v1/devices/{deviceId}/push`

```bash
curl -s -X PUT "$BASE/v1/devices/3f0c9a2e-7d41-4b8e-9a0c-6e5f1d2c3b4a/push" -H "$AUTH" \
  -H "Content-Type: application/json" \
  -d '{"endpoint":"https://ntfy.example.com/enitor-your-topic?up=1"}'
```

Тело — `{"endpoint": "<URL>"}`, или `{"endpoint": null}`, чтобы снять адрес.
После изменения сервер ждёт секунду, поэтому серия правок становится одним
сигналом. Затем он шлёт `POST <endpoint>` с телом `{"rev":124}` на каждый адрес.
Адрес, который ответил 404 или 410, сервер забывает.

## Безопасность

- **Токен** — единственный замок. Это один случайный секрет из 43 символов.
  Держи его в тайне и не клади в ссылки и логи. Если он утёк, останови сервер,
  удали файл `token` в папке данных и запусти сервер снова: создастся новый
  токен. Потом переподключи все устройства с новым токеном.
- **HTTPS вне дома.** Обычный HTTP передаёт токен и данные открыто. HTTP используй
  только внутри домашней сети.
- **CORS — `*`.** Сервер отдаёт `Access-Control-Allow-Origin: *`, поэтому страница
  с любого сайта может к нему обратиться. Здесь это безопасно, потому что cookie
  сервер не использует: страница работает с API только с токеном, а токен ей надо
  передать.
- **Данные на сервере не зашифрованы.** `enitor-data.json` — обычный JSON. Любой,
  кто может прочитать папку данных, прочитает и твои данные. Защити папку
  правами системы и делай бэкапы.
- **Веб-страница на `/`** — простой интерфейс на один день. Она просит токен и
  хранит его в локальном хранилище браузера. Открывай её только на доверенных
  устройствах.
- Своему серверу ты доверяешь сам. Enitor проверяет его только по токену и по
  формату записей.

## Файлы

В папке данных:

- `enitor-data.json`: все записи, ревизии, пометки удалений и адреса push-сигналов.
  Сервер пишет его через `enitor-data.json.tmp` и переименовывает, поэтому
  прерванное сохранение не портит файл.
- `token`: токен. Создаётся при первом запуске или записывается опцией `--token`.
